# Чеклист веток и релизов

Этот документ нужен для двух классов проблем:

1. в продуктовой ветке после merge показывается не то приложение;
2. GitHub Pages открывает `index.html`, но не может загрузить актуальные ассеты.

## Когда проверять этот чеклист

Проверяй его в трех случаях:

1. перед push в `main`, `core` или `member/*`;
2. сразу после merge `main` или `core` в продуктовую ветку;
3. если локально все работает, а опубликованная страница не открывается.

## Соответствие веток и URL

- `main` -> `https://kosdesignsystem.github.io/aiui/`
- `core` -> `https://kosdesignsystem.github.io/aiui/core/`
- `member/NC` -> `https://kosdesignsystem.github.io/aiui/nc/`
- `member/AE` -> `https://kosdesignsystem.github.io/aiui/ae/`
- `member/MK` -> `https://kosdesignsystem.github.io/aiui/mk/`

Перед публикацией всегда проверяй, что изменения делаются именно в той ветке, чей URL нужен.

## Как не потерять нужное приложение в ветке

Источник правды для набора приложений и экранов в ветке — `src/web/registry.ts`.

Перед push:

1. проверь `src/web/registry.ts`;
2. проверь, что в registry остались только те приложения, которые должны быть в этой ветке;
3. проверь `title`, `id` и список `screens` для ветки;
4. проверь, что первый экран в registry действительно должен открываться по умолчанию;
5. после merge из `main` или `core` повтори проверку registry еще раз, даже если конфликтов не было.

Важно:

- merge без конфликта не гарантирует, что веточная конфигурация сохранилась;
- если в `main` и в продуктовой ветке разные наборы приложений, `src/web/registry.ts` нужно проверять вручную после каждого merge;
- наличие файлов в `src/web/<AppName>` не означает, что приложение реально подключено: если его нет в `src/web/registry.ts`, оно не попадет в навигацию и маршруты.

## Как не сломать GitHub Pages

При копировании `dist` в `gh-pages` нельзя полагаться только на размер файла и время изменения. Если `index.html` изменился только по хэшам ассетов, но остался той же длины и попал в ту же секунду, обычный `rsync -av` может пропустить обновление.

Безопасное правило:

1. при публикации в `gh-pages` используй checksum-сравнение, например `rsync -avc --delete`;
2. не заменяй checksum-проверку на сравнение только по `mtime` и размеру;
3. если меняешь workflow деплоя, отдельно проверь сценарий, где меняются только имена файлов в `assets`.

## Что проверить после деплоя

1. открой нужный URL ветки;
2. проверь, что `index.html` и файлы в папке `assets/` ссылаются на одни и те же хэши;
3. если HTML открывается, но приложение пустое, сначала проверь существование JS и CSS из `index.html`;
4. если `index.html` ссылается на отсутствующие файлы, проблема почти наверняка в публикации артефактов, а не в React-коде;
5. если локально все работает, а прод нет, сравни локальный `dist/index.html` с опубликованным `index.html`.

## Минимальный pre-release чек

1. `npm run build` проходит локально;
2. `src/web/registry.ts` соответствует назначению текущей ветки;
3. ветка публикуется в правильный подкаталог Pages;
4. workflow деплоя копирует артефакты с checksum-проверкой;
5. после публикации live `index.html` указывает на существующие JS и CSS файлы.
