# Этап 1. React → Flutter для проверки в браузере на Mac

Используй этот документ для переноса приложения из `src/web` во Flutter, который пользователь сможет открыть и протестировать в браузере на MacBook. Обычный запрос «экспортируй во Flutter» запускает этот этап.

Результат — укомплектованное Flutter-приложение: экраны, состояния, сценарии, навигация, стили, оригинальные ассеты, шрифты и зависимости. Это же приложение затем адаптируется под KOS по [flutter-to-kos.md](../../flutter-to-kos/SKILL.md). Упаковка и сборка KPA относятся ко второму этапу.

## 1. Определи источник и целевой проект

1. Определи React-источник: обычно `src/web/<AppName>`. Если указан один экран, переноси его и необходимые зависимости; если приложение — все его экраны.
2. Изучи используемые `src/ui`, `src/styles`, `src/animate`, `src/assets`, регистрацию экранов и оболочку `src/system`.
3. Составь перечень экранов, маршрутов, состояний и пользовательских сценариев. Учти loading, empty, error, disabled, pressed, модальные окна и переходы.
4. Используй один целевой проект `app/<AppName>/files`. Если он уже существует, обновляй его на месте. Явно указанный пользователем целевой путь имеет приоритет.
5. Сохраняй компоновку, пригодную для второго этапа:

```txt
app/<AppName>/
└── files/
    ├── lib/
    │   └── main.dart
    ├── assets/
    │   ├── icons/
    │   ├── app_icons/
    │   ├── images/
    │   └── fonts/
    ├── web/
    ├── assets-manifest.json
    ├── pubspec.yaml
    ├── pubspec.lock
    └── README.md
```

6. Весь исходный Dart-код приложения размещай в `files/lib`; тесты, если нужны, — в `files/test`. Не импортируй код из других Flutter-приложений и не создавай общий каталог Flutter-компонентов без отдельного решения пользователя.
7. Существующие `Config.in`, mk-файл, `files/CMakeLists.txt` и `files/resources` сохраняй. Для первого этапа создавать их не обязательно.

## 2. Подготовь запускаемый Flutter-проект

1. Используй `rules/minimal_flutter/files/pubspec.yaml` как основу комплектации и заранее учитывай ограничения будущего KOS SDK. Сохраняй `flutter`, `flutter_test`, `flutter_lints` и диапазон Dart SDK шаблона `>=2.12.0 <4.0.0`; проверяй фактическую совместимость выбранных версий зависимостей и используемых API.
2. Имя Dart-пакета в `pubspec.yaml` должно быть допустимым `lowercase_with_underscores`. Имя каталога приложения может отличаться; запиши соответствие в README.
3. Добавь web-платформу. Если она отсутствует, из `files` разрешено выполнить `flutter create --platforms=web --project-name <dart_package_name> .`. Перед генерацией сохрани существующие файлы и проверь изменения после нее: не перезаписывай код приложения, ассеты, pubspec и KPA-настройки шаблонными данными.
4. Не создавай отдельное демо-приложение для браузера и не добавляй macOS-платформу ради запуска в браузере.
5. Зафиксируй зависимости в `pubspec.lock`, версии Flutter/Dart и команды запуска в README. Не выбирай зависимость только ради web, если она делает перенос под KOS невозможным; известные ограничения укажи сразу.

## 3. Перенеси приложение полностью

1. Перепиши JSX и React-компоненты на Dart/Flutter widgets. Не используй WebView, React или исходные HTML/CSS/JS как runtime-слой интерфейса. Служебная web-оболочка и скомпилированный Flutter web допустимы.
2. Перенеси layout через `Column`, `Row`, `Stack`, `Positioned`, `Expanded`, `Flexible`, `Padding`, `Align`, `SizedBox` и scroll-виджеты.
3. Перенеси токены цветов, размеров, отступов, радиусов, теней и типографики в тему и константы внутри `files/lib`. Для Material UI используй `MaterialApp` и `ThemeData` с явной настройкой под исходные токены.
4. Сохрани состояния и события: `useState` → состояние Flutter, derived values → вычисления, эффекты → соответствующий lifecycle с освобождением ресурсов в `dispose`.
5. Реализуй клики, ввод, фокус, клавиатуру, скролл, свайпы, анимации, модальные окна и навигацию. Для проверки на Mac предусмотрены мышь, трекпад и клавиатура.
6. Сохрани мобильную область и safe areas исходника. Для стандартной рамки этого репозитория учитывай `360×800`, верхнюю область `40` и нижнюю `52`, если целевой экран не задает другие параметры. Не добавляй системные отступы дважды.
7. Подготовь данные, конфигурацию, локализацию и ресурсы уже на этом этапе. Реализованное в источнике поведение нельзя откладывать до KOS-адаптации.
8. Платформенные операции вынеси за интерфейсы внутри `files/lib`, чтобы web и KOS использовали общие экраны и логику. Если аппаратная функция недоступна в браузере, добавь явно описанный демо-адаптер с воспроизводимыми состояниями; перечисли такие адаптеры и ограничения в README.

## 4. Перенеси оригинальные ассеты

Прочитай [правила переноса и реестра](assets.md), перенеси ресурсы и проверь их скриптом. Правила общие для обоих этапов.

## 5. Проверь запуск и передай пользователю

Из `files` выполни:

```sh
flutter pub get
dart format lib
flutter analyze
flutter build web
flutter run -d chrome
```

1. Проверь открытие приложения в браузере, доступность ассетов, отсутствие ошибок загрузки и работу основных сценариев. Визуальное сравнение и сравнение скриншотов не выполняй.
2. Проверь комплектность ресурсов по реестру, совпадение SHA-256 скопированных файлов и сохранение SVG-параметров у извлеченных ресурсов.
3. Если есть содержательные тесты логики и сценариев, выполни `flutter test`. Не добавляй формальные тесты только ради чеклиста.
4. В README укажи рабочую директорию, необходимые версии инструментов, команды установки зависимостей, запуска в Chrome и сборки web, список сценариев, демо-адаптеров и известных ограничений. Для запуска в другом браузере можно описать `flutter run -d web-server` и открытие выданного локального URL; не предлагай открывать `build/web/index.html` через `file://`.
5. В ответе дай путь к проекту, точную команду запуска на Mac и результаты проверок. Если сервер запущен, укажи фактический URL. Если инструменты или зависимости недоступны, перечисли невыполненные проверки и не называй запуск подтвержденным.
6. На этом заверши первый этап и передай приложение пользователю для тестирования. Переходи к [этапу 2](../../flutter-to-kos/SKILL.md) по запросу на KOS-адаптацию; обычный запрос «экспортируй во Flutter» не запускает второй этап автоматически. При явном запросе обоих этапов выполняй их последовательно, сохраняя браузерный результат.

## Чеклист этапа 1

1. Все выбранные экраны, состояния и сценарии перенесены в Dart/Flutter.
2. Приложение укомплектовано ресурсами, шрифтами, данными и зависимостями; ограничения браузерных адаптеров описаны.
3. Оригинальные SVG перенесены, реестр и контрольные суммы проверены; замены и перерисовки отсутствуют.
4. Web-версия использует тот же код и ассеты, которые пойдут на второй этап.
5. Выполнены доступные проверки анализа, сборки, запуска и сценариев без визуального сравнения.
6. Пользователь получил инструкцию для самостоятельного тестирования на Mac.
