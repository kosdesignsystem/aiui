# Этап 2. Проверенный Flutter → KOS/KPA для передачи в разработку

Используй этот документ, когда пользователь просит адаптировать Flutter-приложение под KasperskyOS for Mobile и подготовить передачу разработчикам. Вход — версия из [этапа 1](../../web-to-flutter/SKILL.md), которую пользователь протестировал или явно выбрал для KOS-адаптации.

Результат — исходный KOS/KPA-проект с инструкцией сборки, зависимостями, оригинальными ассетами и описанием платформенных интеграций. При доступном SDK дополнительно собери KPA. Недоступность SDK не мешает подготовить исходники для передачи, но не позволяет заявлять об успешной KOS-сборке.

## 1. Продолжай тот же проект

1. Зафиксируй входную версию Flutter-приложения и результаты его проверки пользователем; используй commit, если он доступен, либо явно опиши выбранное состояние файлов.
2. Если первого этапа нет, выполни [web-to-flutter.md](../../web-to-flutter/SKILL.md). Не переписывай React сразу в отдельную KOS-реализацию и не пропускай браузерный результат без явного указания пользователя.
3. Обновляй тот же `app/<AppName>` на месте. Не создавай копию приложения с отдельными экранами, логикой и ресурсами для KOS.
4. Сохраняй работоспособность браузерного запуска. Изменения этого этапа касаются KPA-упаковки, совместимости SDK и платформенных адаптеров; не меняй согласованные сценарии и оформление без соответствующего запроса.
5. Используй `rules/minimal_flutter` как эталон KPA-компоновки и сборочных файлов. Добавляй недостающие файлы, не перезаписывая готовые `files/lib`, `files/assets`, pubspec и README демо-содержимым шаблона.

```txt
app/<AppName>/
├── Config.in
├── <app_name>.mk
└── files/
    ├── CMakeLists.txt
    ├── lib/
    │   └── main.dart
    ├── assets/
    ├── web/
    ├── assets-manifest.json
    ├── pubspec.yaml
    ├── pubspec.lock
    ├── README.md
    └── resources/
        ├── icons/
        │   └── flutter.png
        └── locale/
            └── names
```

`<AppName>` — существующий каталог приложения, `<app_name>` — согласованный идентификатор KPA-пакета. Сохраняй существующее именование; если идентификатор отличается от каталога или Dart package name, явно запиши соответствие в README и настрой интеграцию с SDK под фактический путь.

## 2. Подготовь обязательные KPA-файлы

### `files/CMakeLists.txt`

```cmake
cmake_minimum_required(VERSION 3.14)

project(<app_name>)

include(platform/flutter)

add_flutter_app(<app_name>
                INCREMENTAL
                KPA
                KPA_DEVELOPER_ID lk
                KPA_ICON resources/icons/flutter.png
                KPA_LOCALE resources/locale/names)
```

1. Согласуй CMake project/target, `package_name` в mk-файле, имя mk-файла и KPA-идентификатор.
2. `include(platform/flutter)`, `INCREMENTAL`, `KPA`, `KPA_DEVELOPER_ID`, `KPA_ICON` и `KPA_LOCALE` обязательны. Используй developer ID проекта; `lk` — значение базового шаблона.
3. Иконка должна реально находиться в `files/resources/icons`, локализованные имена — в `files/resources/locale/names`.
4. Для иконки пакета используй подготовленный оригинальный ресурс приложения подходящего для SDK формата и обнови `KPA_ICON`, если путь отличается. Не оставляй шаблонную Flutter-иконку вместо существующей иконки приложения. Если подходящего файла нет, укажи недостающий ресурс без самостоятельной перерисовки.

### `files/pubspec.yaml` и зависимости

1. Сохрани pubspec и lockfile первого этапа, включая SVG-рендерер, ассеты, шрифты, `flutter`, `flutter_test`, `flutter_lints` и `uses-material-design` при использовании Material UI.
2. Базовый диапазон Dart SDK шаблона — `>=2.12.0 <4.0.0`. Не расширяй его ради обхода несовместимости; проверь фактические версии Dart/Flutter в целевом KOS SDK, требования пакетов и используемые API.
3. Все изображения и SVG из `files/assets` должны быть явно перечислены в `flutter.assets`, шрифты — в `flutter.fonts` с нужными начертаниями.
4. Проверь совместимость каждого плагина, особенно платформенных каналов и SVG-рендерера. Успешный запуск в Chrome не доказывает поддержку KOS.
5. Если нужны другие совместимые версии пакетов, зафиксируй их, обнови lockfile в соответствующем окружении и повтори проверку web. Не удаляй SVG-поддержку ради сборки и не заменяй ресурсы рисованием.

### `<app_name>.mk`

```make
package_name  := <app_name>
dir           := $(call my_dir)

dependencies  := components/flutter

NO_LOCALIZE   := y

$(call set_env_var,PUB_HOSTED_URL,$(PUB_HOSTED_URL),TRUE)
$(if $(call is_equal,$(USE_PREBUILT_SDK),y), ,$(call set_env_var,PUB_CACHE,$(PUB_CACHE),TRUE))

include $(KB_SRCDIR)/templates/build_example.mk
```

`components/flutter`, настройки `PUB_HOSTED_URL` и `PUB_CACHE` обязательны. Не заменяй этот файл сборкой обычного Flutter desktop-приложения.

### `Config.in` и локализованные имена

1. Перенеси `Config.in` из `rules/minimal_flutter` с поддержкой указанных там KOS-архитектур.
2. Обнови `menuconfig`, соответствующие условия `if`, человекочитаемый заголовок, `#define NAME` и `PACKAGE_PROPERTY(PREFIX)` под фактическую интеграцию приложения в дерево SDK.
3. В `files/resources/locale/names` укажи как минимум:

```txt
ru=<Название приложения>
en=<Application name>
```

## 3. Адаптируй платформенные интеграции

1. Подключи реализации платформенных интерфейсов, предусмотренных на первом этапе: хранение, сеть, файловые операции, системная навигация и аппаратные функции, если они нужны приложению.
2. Изолируй браузерные зависимости в web-адаптерах. KOS-сборка не должна импортировать web-only API; выбор реализации организуй через подходящие для проекта условные импорты или точки входа внутри `files/lib`.
3. Не оставляй React, WebView, HTML/CSS или исходный JavaScript в качестве runtime-реализации KOS-интерфейса.
4. Для каждой интеграции укажи статус: реализована и проверена, реализована без проверки на устройстве либо требуется реализация разработчиками. Демо-адаптер нельзя выдавать за работающий KOS-сервис.
5. Если для завершения функции не хватает API, SDK или доступа к устройству, сохрани понятный контракт и перечисли конкретные недостающие работы. Не объявляй приложение полностью готовым к эксплуатации при наличии таких ограничений.

## 4. Сохрани ассеты первого этапа

Прочитай [общие правила ресурсов](../../web-to-flutter/references/assets.md) и выполни проверку для второго этапа. Используй реестр и оригинальные файлы проверенной Flutter-версии. Не генерируй ресурсы заново и не обновляй контрольные суммы для обхода ошибок проверки.

## 5. Выполни доступные проверки

Из `files` в подходящем Flutter-окружении:

```sh
flutter pub get
dart format lib
flutter analyze
flutter build web
```

1. Выполни существующие содержательные тесты через `flutter test`, если они есть. Проверь, что браузерный запуск и основные сценарии первого этапа сохранились.
2. В дереве KasperskyOS for Mobile SDK используй штатную сборку нужной архитектуры, например:

```sh
./cross-build.x86_64-pc-kos.sh
./cross-build.aarch64-kos.sh
```

3. Команды выше — примеры из шаблона. Укажи фактическую рабочую директорию, подключение пакета в дерево SDK и точную команду целевой сборки. Собирай требуемую архитектуру; не заявляй о проверке остальных автоматически.
4. При доступном устройстве или эмуляторе проверь установку KPA, запуск, загрузку ресурсов и основные сценарии. Если окружение недоступно, явно отдели подготовку исходников от подтвержденной сборки и проверки на устройстве.
5. Запуск `flutter run -d chrome` и успешная web-сборка не заменяют KPA-сборку. Не выдавай `build/web` за результат второго этапа.

## 6. Подготовь передачу в разработку

Обнови `files/README.md`, сохранив инструкцию браузерного запуска, и включи:

1. Исходное React-приложение, входную Flutter-версию, состав перенесенных экранов и сценариев.
2. Версии KOS SDK, Flutter/Dart, зависимости и lockfile; если версия SDK неизвестна, прямо укажи это.
3. Соответствие каталога, Dart package name, CMake target, mk-пакета и KPA ID.
4. Структуру проекта, подключение к дереву SDK, команды сборки и требуемую архитектуру.
5. Ссылку на assets-manifest.json, происхождение ресурсов, способ проверки контрольных сумм и настройки SVG-рендеринга.
6. Платформенные адаптеры, конфигурацию, доступы и конкретные оставшиеся задачи разработчиков.
7. Выполненные проверки с результатами и отдельно невыполненные проверки с причинами.
8. Фактический путь к KPA, если он собран. Не придумывай артефакт или его наличие по ожидаемому имени.

В ответе пользователю дай путь к исходному KOS-проекту и README, статус KPA-сборки и оставшиеся интеграции. Если пакет собран, добавь путь к артефакту.

## Чеклист этапа 2

1. Адаптирована выбранная версия первого этапа в том же проекте, браузерный запуск сохранен.
2. Структура и обязательные KPA-файлы соответствуют `rules/minimal_flutter`; идентификаторы согласованы.
3. Зависимости и платформенные адаптеры проверены на совместимость с целевым SDK либо ограничения явно описаны.
4. Оригинальные ассеты сохранены, контрольные суммы проверены; перерисовок и замен нет.
5. Результаты анализа, web-проверки, KPA-сборки и запуска на устройстве отражены раздельно, без визуального сравнения.
6. Исходники, инструкции и список оставшихся работ готовы к передаче разработчикам.
