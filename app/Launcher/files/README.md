# Launcher — Flutter / KOS / KPA: передача разработчикам

Проект: `/Users/kasper/aiui/app/Launcher/files`. Dart package: `launcher`.
Источник: `src/web/Launcher` и его зависимости из `src/ui`, `src/system`,
`src/animate`, `src/web/LoadingApp`. Доступный из шторки маршрут
`/app/Components/navigation` также перенесён из `src/web/Components/navigation.tsx`.

Это самостоятельное приложение на Dart/Flutter. React, HTML/CSS исходного
интерфейса, Vite и WebView во время работы не используются. Общие экраны,
логика и ресурсы находятся в `lib` и `assets`; отдельной реализации web-демо нет.
Вход второго этапа — проверенное пользователем рабочее дерево Flutter на
21 октября 2026 года поверх commit `9ef3446a1af0c80953d0ec46d7ce4350c20cb9f0`.
Оно содержало незакоммиченные изменения, поэтому один commit не описывает
входную версию. `stage1-input.json` фиксирует SHA-256 всех 84 входных файлов
Flutter-проекта, исключая кэши и сборки; это запись происхождения, а не архив.
Эталон ресурсов остаётся прежним: `assets-manifest.json` не пересоздавался.

В том же `app/Launcher` восстановлена KPA-компоновка по
`rules/minimal_flutter`, подключён выбор платформенного адаптера и его передача
из `LauncherApplication` в шторку и Navigation. Экраны, жесты, сценарии,
оригинальные ассеты и браузерная точка входа сохранены.

**Статус передачи:** исходники подготовлены; KPA не собран. KasperskyOS for
Mobile SDK и `kosctl` не обнаружены в PATH, `/opt`, `/usr/local`, каталоге
`/Users/kasper/dev` и проекте. Docker CLI есть, но daemon недоступен
(`/var/run/docker.sock` отсутствует); наличие SDK в выключенных контейнерах
не установлено. Версия KOS SDK неизвестна. KOS-эмулятор/устройство недоступны;
установка, нативный рендеринг и работа системных сервисов не проверены.
Доступный Flutter — обычный macOS SDK, а не Flutter из KOS SDK.

## Запуск на Mac

Проверяемая среда: Flutter **3.41.1**, stable, revision `582a0e7c55`,
Dart **3.11.0**, Google Chrome. SDK на этом Mac расположен в
`/Users/kasper/dev/flutter`. Можно использовать его явно:

```sh
cd /Users/kasper/aiui/app/Launcher/files
export PATH="/Users/kasper/dev/flutter/bin:$PATH"
flutter pub get --enforce-lockfile
flutter run -d chrome --web-hostname 127.0.0.1 --web-port 8736
```

После запуска Chrome откроется автоматически. Адрес: `http://127.0.0.1:8736`.
Сервер работает, пока открыт процесс `flutter run`; для остановки нажмите `q`
в его терминале. Если порт занят, измените `--web-port`.

Для другого браузера:

```sh
flutter run -d web-server --web-hostname 127.0.0.1 --web-port 8736
```

Откройте выданный URL в браузере. Не открывайте `build/web/index.html` через
`file://`. Для просмотра production-сборки:

```sh
flutter build web --no-pub
python3 -m http.server 8737 --bind 127.0.0.1 --directory build/web
```

Адрес production-сборки: `http://127.0.0.1:8737`. Для остановки этого сервера — Ctrl+C.
Первая загрузка Flutter web может потребовать доступ к ресурсам движка Google;
оригинальные ассеты приложения включены в сборку и не загружаются из React/Vite.

## Проверка вручную

Интерфейс имеет логическую область 360×800, верхнюю область 40 и нижнюю 52.
Область вписывается в окно с сохранением пропорций. Системные отступы не
дублируются. Для свайпа мышью или трекпадом зажмите основную кнопку и
перетащите указатель. Ползунки также управляются стрелками, Home и End;
кнопки доступны через Tab, Shift+Tab, Enter и пробел.

1. На блокировке проведите вверх более чем на 64 логических пикселя.
   Введите любые четыре цифры: исходник проверяет только количество цифр.
   До четвёртой цифры проверьте «Отменить»: возврат на блокировку и сброс PIN.
   «Не помню» и SOS оставлены без действия, как в React.
2. На первой странице откройте по очереди Камеру, Телефон, Погоду, Файлы,
   Настройки и Галерею. Проверьте загрузочный переход и возврат системной
   кнопкой «Домой». Светлая/тёмная строка статуса зависит от приложения.
3. Перелистните рабочий стол влево или нажмите второй индикатор.
   Там находятся остальные 15 иконок; они неактивны, как в источнике.
   Вернитесь первым индикатором или свайпом вправо. Короткий свайп должен
   возвращать страницу на место, свайп за краем — давать сопротивление.
4. На рабочем столе проведите вниз более чем на 72 пикселя. Переключите
   мобильный интернет, Wi-Fi, режим полёта, геолокацию, беззвучный режим и
   фонарик. Проверьте подписи Megafon LTE / KLCorp / «Выключено», цвета,
   анимации оригинальных иконок и состояния выключения.
5. Измените громкость и яркость. Цвета иконок на заполнении меняются на
   порогах 9% и 91%; ползунок не должен запускать системный свайп.
   Закройте шторку свайпом вверх или нажатием области «Закрыть панель»
   над системной навигацией. При повторном открытии демо-настройки
   сбрасываются — это поведение React-компонента при размонтировании.
6. Повторите открытие и закрытие шторки поверх приложения: после закрытия
   должен восстановиться тот же экран приложения. Проверьте «Домой» из
   открытой шторки и из приложения.
7. На рабочем столе или в приложении проведите вверх более чем на 72 пикселя.
   В недавних перелистывайте карточки горизонтально; активная карточка
   крупнее соседних. Нажмите карточку для возврата в приложение. Смахните
   карточку вверх более чем на 88 пикселей или коротким быстрым жестом,
   чтобы удалить её. Проверьте «Закрыть все» и удаление последней карточки:
   возврат на рабочий стол. При повторном открытии недавних исходный
   демонстрационный список из шести карточек восстанавливается.
8. В шторке нажмите «Перейти в настройки». В исходнике эта кнопка открывает
   каталог **Navigation**, а не PNG приложения «Настройки»; маршрут сохранён.
   Проверьте Header (Action/Meta/Long title), Tabs и SegmentedTabs
   (Active tab/Action button/Interactive/Disable last tab), Nav
   (Active item/Labels/Disable last item), копирование конфигурации,
   прокрутку и возврат через «Назад» или «Домой».
9. Обновление страницы перезапускает демо с блокировки. Время `13:52`, дата
   «Понедельник, 24 июня» и заряд `98%` фиксированы исходником, не системные.
   В каталоге сохранены значения внешней оболочки `09:41` и `96%`.

## Ресурсы

В `assets-manifest.json` перечислены **59** файлов: 55 побайтовых копий и
4 механически извлечённых SVG. Это 21 PNG-иконка приложений, 6 PNG-экранов,
обои, 4 оригинальных файла шрифтов, 23 SVG из `src/assets/icons` и 4 inline SVG.
Все изображения и SVG явно зарегистрированы в `pubspec.yaml`, оригинальные
шрифты Kaspersky Sans Text (400/500/600, WOFF2) и Clock (400, OTF) — в `fonts`.

Оригиналы SVG не изменены, не растеризованы и не заменены библиотечными
иконками. `OriginalIcon` при рендеринге связывает монохромный paint `#212529`
с токеном состояния, аналогично `scripts/build-icons.mjs` + `src/ui/Icon.tsx`.
Остальные краски, прозрачности и градиенты не перекрашиваются общим фильтром.

Inline SVG: ручка разблокировки из `launcher.tsx`, сотовые сегменты и два
состояния Wi-Fi из `shade.tsx`. Скрипт `tool/prepare_assets.py` механически
переводит JSX-атрибуты в XML и добавляет presentation-атрибуты из `_home.scss`
и `_shade.scss`. Он проверяет порядок XML-узлов и все исходные атрибуты,
включая viewBox, rect/circle, пути, градиент и его ссылки. Проверка независима
от контрольных сумм. Анимации применяются к исходным SVG-элементам при
рендеринге, без изменения файлов ассетов.

Из корня репозитория:

```sh
python3 .agents/skills/web-to-flutter/scripts/verify_assets.py \
  app/Launcher/files/assets-manifest.json --repo-root . \
  --app-root app/Launcher/files
python3 app/Launcher/files/tool/prepare_assets.py --check
```

`--check` только читает файлы, сверяет копии/геометрию, реестр и комплектность.
Запуск `prepare_assets.py` без `--check` предназначен для осознанного нового
переноса обновлённого источника: он перезаписывает ассеты и эталонный реестр.
Не используйте его для обхода проверки контрольных сумм на втором этапе.

## Зависимости и совместимость SDK

Проверено на Flutter **3.41.1**, revision `582a0e7c55`, Dart **3.11.0**.
В `pubspec.yaml` сохранён диапазон `>=2.12.0 <4.0.0`; он не означает,
что код и все зависимости работают на Dart 2. Фактический lockfile требует
**Dart >=3.9.0** и **Flutter >=3.32.0**. Более старый KOS SDK требует отдельного
согласования совместимых зависимостей/API и повторной проверки web.

| Зависимость | Версия / роль | Проверка на KOS |
| --- | --- | --- |
| `flutter` / `flutter_test` | из выбранного SDK | Нужны версии из KOS SDK и соответствующие pin-зависимости |
| `flutter_svg` | 2.2.3, оригинальные SVG и `ColorMapper` | Нативных плагинов нет; нужно проверить движок и SVG на KOS |
| `vector_graphics` / codec / compiler | 1.1.19 / 1.1.13 / 1.2.0 | Compiler задаёт минимум Dart 3.9; поддержка рендеринга не подтверждена |
| `xml` / `path_parsing` / `petitparser` | 6.6.1 / 1.1.0 / 7.0.2 | Dart-пакеты; разрешение зависимостей проверить целевым SDK |
| `http` | 1.6.0, тестовый транспорт и транзитивная зависимость SVG | Runtime использует локальные ресурсы; сеть устройства не проверена |
| `flutter_lints` | 4.0.0, dev dependency | Проверить в окружении SDK |

Остальные точные версии и SHA-256 пакетов — в `pubspec.lock`.
При повторной проверке входной lockfile не прошёл `--enforce-lockfile`:
установленный Flutter требует `characters 1.4.0` вместо 1.4.1,
`matcher 0.12.17` вместо 0.12.18, `material_color_utilities 0.11.1` вместо
0.13.0 и `test_api 0.7.7` вместо 0.7.9. Только эти четыре версии и их
контрольные суммы согласованы с установленным Flutter. Прямые зависимости,
`flutter_svg`, ресурсы и диапазон SDK сохранены. Повторная строгая проверка
lockfile проходит. В KOS SDK при других pin-версиях нельзя просто ослаблять
ограничения: разрешить совместимые версии его Flutter, сохранить lockfile
и повторить анализ, сценарии и web-сборку.

WOFF2 (Kaspersky Sans Text) и OTF (Clock) сохранены без изменений. Их нативную
загрузку, SVG-конструкции/градиенты/анимации и `BackdropFilter` проверить на
движке целевого KOS SDK. При неподдерживаемом WOFF2 запросить исходный TTF/OTF
того же семейства и начертаний. Не подменять шрифт или оригинальные иконки.

## Подключение и сборка в KasperskyOS for Mobile SDK

Штатная система SDK должна сначала зарегистрировать пакет и подготовить
пример со своими CMake-модулями и cross-build-скриптами. Обычная команда
`cmake` или Flutter desktop не создаёт KPA.

1. В рабочем дереве **целевого** SDK найдите регистрацию `minimal_flutter`:
   `rg -n minimal_flutter "$KOS_SDK_ROOT"`. Сверьте её с поставленным SDK
   шаблоном; локальный эталон находится в `rules/minimal_flutter`.
2. Подключите **тот же** `app/Launcher` в каталог
   `$KOS_SDK_ROOT/examples/projects/mobile/kpa/Launcher` (например, symlink
   на исходники). Для контейнера смонтируйте репозиторий так, чтобы ссылка
   разрешалась внутри него. Не создавайте отдельную реализацию `lib/assets`.
3. В агрегирующих Config.in/списках пакетов SDK зарегистрируйте
   `Launcher/Config.in` и `Launcher/Launcher.mk` по образцу `minimal_flutter`.
   Существующую регистрацию других пакетов сохраняйте. Выберите
   `KB_examples_projects_mobile_kpa_Launcher=y`, зависимость `components/flutter`
   и архитектуру штатным конфигуратором SDK. При другом дереве синхронно
   измените config symbol, NAME и PREFIX, а не только путь к mk-файлу.
4. Выполните штатную подготовку/экспорт SDK-примера. Ожидаемый каталог
   экспортированного примера по `Config.in`:
   `$EXAMPLES_PREFIX_DIR/mobile/kpa/Launcher`. Он должен содержать этот
   `files/CMakeLists.txt`, `lib`, `assets`, `resources`, pubspec/lockfile,
   SDK CMake-модули и сгенерированные/поставленные SDK cross-build-скрипты.
   Убедитесь, что это актуальные исходники второго этапа.
5. Используя **Flutter из KOS SDK**, проверьте его версии и зависимости
   до cross-build: `flutter --version`, `dart --version`,
   `flutter pub get --enforce-lockfile`, `flutter analyze --no-pub`.
   Для offline-сборки заранее наполните PUB_CACHE и настройте PUB_HOSTED_URL
   средствами SDK; не удаляйте `flutter_svg` ради обхода ошибок разрешения.

Далее рабочая директория — **экспортированный пример Launcher**, а не корень
этого репозитория и не произвольный каталог SDK. Пример команд для x86-64
(эмулятор; после описанной подготовки):

```sh
export LAUNCHER_SDK_PROJECT="$EXAMPLES_PREFIX_DIR/mobile/kpa/Launcher"
cd "$LAUNCHER_SDK_PROJECT"
test -f CMakeLists.txt
test -x cross-build.x86_64-pc-kos.sh
./cross-build.x86_64-pc-kos.sh
find "$PWD/build.x86_64-pc-kos" -type f -name '*.kpa' -print
```

Для arm64 (физическое устройство; выполняйте вместо x86-64):

```sh
cd "$LAUNCHER_SDK_PROJECT"
test -x cross-build.aarch64-kos.sh
./cross-build.aarch64-kos.sh
find "$PWD/build.aarch64-kos" -type f -name '*.kpa' -print
```

Эти имена скриптов и каталогов взяты из README `rules/minimal_flutter`.
В репозитории cross-build-скриптов нет: их должен предоставить SDK, а не
созданный здесь неподтверждённый toolchain. Точная команда регистрации и
подготовки примера, пути агрегирующих конфигураций, версия SDK и фактический
EXAMPLES_PREFIX_DIR не установлены без SDK; интегратор должен зафиксировать
их после подключения. Команды выше не были выполнены как KOS-сборка.

Целевую архитектуру пользователь не указал; приведены оба варианта без
утверждения об их сборке. Config.in сохраняет также arm и i686 из шаблона,
но инструкции их cross-build не подтверждены. Ожидаемый пакет по шаблону —
`build.<target>/kpa/lk.Launcher.kpa`; это **ожидаемый**, а не существующий
артефакт. Фактический путь KPA: **отсутствует, пакет не собран**.

После успешной сборки используйте `kosctl` из того же SDK. Для эмулятора
сначала выберите реально установленный образ через `kosctl emu list-firmware`,
запустите его `kosctl emu start <image>` и проверьте `kosctl device list`.
Установка: `kosctl app install -d <device> <фактический-путь-к-KPA>`.
Не устанавливайте arm64-пакет в x86-64-эмулятор. После установки проверьте
значок/локаль, запуск, загрузку всех ресурсов и сценарии из раздела ручной
проверки, затем ошибки неподключённых сервисов. Визуальное сравнение и
сравнение скриншотов не выполнялись.

## Платформенные контракты и оставшиеся интеграции

`lib/platform/launcher_platform.dart` содержит контракт `LauncherPlatform`:
`createControls()` возвращает новую модель состояния при открытии шторки;
`copyText(String)` завершается только при успешной записи и пробрасывает ошибку.
`launcher_platform_factory.dart` выбирает браузерный `DemoLauncherPlatform`
при `kIsWeb`, иначе — `KosLauncherPlatform`. Все импорты runtime — переносимые
Dart/Flutter; `dart:html`, JS, React/WebView и web-only API в `lib` отсутствуют.
Транзитивный пакет `web` нужен web-ветке `http`; сам факт наличия в lockfile
не означает импорт браузерных API в нативное приложение.

Выбранный адаптер передаётся через `LauncherApplication(platform: ...)` →
`LauncherScreen` → `ControlShade` и `NavigationCatalog`. Браузерный адаптер
сохраняет Flutter Clipboard и демо-поведение. `KosLauncherPlatform` сохраняет
локальную модель и принимает `ClipboardWriter`; без подключённого bridge
копирование выбрасывает `UnsupportedError`. Navigation ловит ошибку и не
показывает успешное копирование. Никакие имена MethodChannel или API KOS
не придуманы. Пример подключения после инициализации **реального** bridge:

```dart
runApp(LauncherApplication(
  platform: KosLauncherPlatform(writeClipboard: bridge.writeClipboard),
));
```

`bridge` в примере должен предоставить интегратор. При работе через async
каналы callback обязан ждать ответа, передавать точную строку и сохранять
ошибки. Flutter Clipboard на KOS можно использовать только после проверки
реализации соответствующего канала embedder; здесь он не считается доступным.

| Интеграция | Фактический статус | Оставшаяся работа |
| --- | --- | --- |
| UI, анимации, жесты, Navigation, модели | Реализованы, проверены локально и в Chrome | Проверить нативные ввод, производительность и доступность на устройстве |
| Выбор/передача адаптера | Реализованы, проверяются тестами | Подключить реальный SDK bridge в точке входа |
| Буфер обмена | Web: Flutter Clipboard; KOS: callback-контракт, системной реализации нет | Реализовать ClipboardWriter, проверить разрешения, Unicode, отказ/недоступность сервиса |
| Wi-Fi / mobile / airplane / location / silent / flashlight | Только локальные demo bool | Реальные чтение/запись, состояния unavailable/denied/pending, подписки на изменения сервисов, политика доступа |
| Громкость / яркость | Только локальные значения 0–100 | Согласовать шкалы SDK, async запись/подтверждение, ошибки и обновление извне |
| Время, дата, заряд, оператор, сеть | Фиксированные значения исходного прототипа | Контракты часов/батареи/телефонии и подписки, если нужен рабочий системный launcher |
| Блокировка / PIN / SOS | Демо: любые 4 цифры; SOS/«Не помню» без действия | Реальная аутентификация, безопасное хранение, ограничения попыток и системный emergency flow |
| Запуск приложений / недавние / Home | Локальная навигация и PNG-превью | Сервис приложений/задач, разрешения запуска/закрытия, системные Home/Back и жизненный цикл |
| Хранение | Персистентности нет; сброс при перезапуске/открытии соответствует исходнику | При новых требованиях определить Storage-интерфейс, область данных и миграции; секреты не хранить в demo-модели |
| Файлы / камера / телефон / галерея / сеть | Только шесть PNG-превью, системные API не вызываются | Подключать отдельные приложения или новые SDK-контракты, если это входит в требования продукта |
| Упаковка и права | CMake/mk/Config.in, локаль и значок подготовлены | Подтвердить developer ID, SDK-регистрацию, подпись/доверие и сервисные capabilities целевого решения |

`ControlState` сейчас — изменяемый UI-снимок: переключатели меняют его поля
синхронно. Это **не контракт управления устройством**. Для реальных сервисов
нужно добавить async операции чтения/записи и поток подтверждённого состояния
на платформенной границе, обновить обработчики `ControlShade`, предусмотреть
отмену подписок/обработку отказов. Одной передачи другой `createControls()`
недостаточно для аппаратной интеграции. До этой работы сохраняется согласованное
демо-поведение, включая сброс настроек при повторном открытии шторки.

Шесть запускаемых приложений остаются оригинальными PNG-превью без внутренних
кнопок, как в React Launcher. Реальная галерея/телефон других приложений
репозитория не выдаются за реализованные в этих превью. KPA — обычное
GUI-приложение; системные роль launcher/lockscreen, init и политики безопасности
решения этим пакетом не устанавливаются и должны быть согласованы отдельно.

## Автоматические проверки

Из каталога `files`:

```sh
flutter pub get --enforce-lockfile
dart format lib test
flutter analyze --no-pub
flutter test --no-pub
python3 tool/test_in_chrome.py
flutter build web --no-pub
```

Браузерная команда временно запускает локальный HTTP-сервер оригинальных
ассетов с CORS и закрывает его после теста. Это требуется тестовому хосту
Flutter; обычному приложению такой адаптер не нужен. Переменная `FLUTTER_BIN`
позволяет указать полный путь к Flutter, если он не находится в PATH.

Сценарные тесты находятся в `test/launcher_scenarios_test.dart`. Они проверяют
декодирование ресурсов, блокировку/PIN, обе страницы, все шесть запусков,
шторку, переключатели, управление ползунками, недавние, Navigation и копирование
конфигурации. Тесты также проверяют промежуточные кадры удаления карточки: отсутствие
обрезания при свайпе, сохранение положения при отпускании, плавный сдвиг
соседней карточки справа или слева и отсутствие скачка в момент удаления.
Сценарий перехода в Navigation также проверяет, что переданный в корне
адаптер достигает шторки и выполняет копирование из каталога. Дополнительные
`test/launcher_platform_test.dart` проверяют отказ неподключённого KOS clipboard,
передачу точной строки bridge и распространение ошибки записи.
Тесты не используют эталонные изображения или сравнение пикселей.
